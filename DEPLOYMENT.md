# Развёртывание и эксплуатация

Актуализировано **22 октября 2026**. Основной пользовательский адрес: **[Telegram Mini App](https://t.me/RPL30_bot?startapp)**. Технический HTTPS-origin приложения: `https://30-0.xn--p1ai` — нужен для API, OAuth, webhook и health-check, а не как основная рекламная ссылка.

## Production

**Jino shared hosting → Apache / Phusion Passenger → Next.js standalone → MySQL/MariaDB.** CI использует Node.js 22. Vercel и отдельный VPS не являются текущей production-схемой. Пути и параметры доступа берутся из приватных настроек окружения; не добавляйте приватные ключи, дампы или `.env` в git.

## CI/CD

`.github/workflows/deploy.yml` запускается на PR, push в main и вручную. PR выполняет проверки без установки на Jino. Для main предусмотрены:

1. ESLint, TypeScript, тесты и валидация вариантов Prisma.
2. Изолированные интеграционные сценарии SQLite.
3. Production build с MySQL-схемой и упаковка standalone.
4. SSH/SCP-загрузка, резервирование предыдущей сборки, проверка данных и синхронизация схемы.
5. Перезапуск Passenger и внешняя проверка главной и `/api/health`.

Проверки, сборка, загрузка и внешний verify — разные стадии. **Зелёная сборка не подтверждает установленный релиз.** Изменения только документации могут публиковаться без нового релиза приложения; при этом PR всё равно должен пройти проверки.

## Переменные и секреты

| Область | Имена | Где хранить |
|---|---|---|
| SSH | `JINO_HOST`, `JINO_USERNAME`, `JINO_SSH_KEY`, `JINO_SSH_PORT`, `JINO_APP_DIR` | GitHub Actions secrets / приватная конфигурация |
| База | `DATABASE_URL` | Закрытое окружение сервера |
| Приложение | `NEXT_PUBLIC_BASE_URL`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_CLIENT_ID` | Публичные идентификаторы, без токенов |
| Подписанные сессии | `TELEGRAM_SESSION_SECRET`, `RUN_SESSION_SECRET`, `ADMIN_SESSION_SECRET` | Отдельные случайные секреты каждого окружения |
| Bot API | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` | Сервер / соответствующие Actions secrets |
| Serverless и relay | `TGCLOUD_TOKEN`, `TELEGRAM_SERVERLESS_BRIDGE_SECRET` | Согласованные закрытые настройки обработчика и Actions |
| Операционные endpoints | `SEED_API_SECRET`, `DEPLOY_WEBHOOK_SECRET` | Только если эти endpoints используются |

Смотрите фактические имена secrets в workflow перед настройкой. Не печатайте их значения в логи. Не заменяйте существующие рабочие `.env` примером: `.env.example` предназначен для нового локального окружения.

## Telegram и очередь

- `.github/workflows/telegram-serverless.yml` разворачивает обработчик отдельно от приложения.
- `.github/workflows/notifications.yml` запускает relay каждые пять минут, после успешного релиза и вручную.
- Основной runner — Ubuntu, резервный — macOS. Расписание GitHub Actions может задерживаться.
- Очередь `TelegramOutbox` хранится в БД. Задания выдаются с арендой и подтверждаются после обработки; повтор не должен терять задачу.
- Перед доставкой учитываются настройки пользователя, статус диалога с ботом и отмена сценария возврата после новой активности.
- Telegram не позволяет боту первым писать пользователю, не начавшему диалог; блокировка бота и отключение уведомлений — отдельные состояния.

### Проверка доставки

Проверяйте цепочку: событие → outbox → выдача relay → отправка Telegram → подтверждение → получение на тестовом устройстве. Используйте отдельный тестовый аккаунт и не запускайте массовую рассылку ради проверки. Успешная регистрация webhook не является доказательством доставки приглашений и результатов. В аудите 22 октября подтверждена локальная логика очереди; реальная доставка повторно не подтверждалась.

## Данные и восстановление

Перед изменением БД нужна приватная резервная копия с проверкой восстановления. Актуальные импортёры: `scripts/import-rpl-2006-2009.mjs`, `2010-2018`, `2019-2021`, `2022-2025`. Сначала запускайте проверку без записи. Применение требует явных `--apply` и нового `--backup=...`. Не запускайте старый seed как замену ручным изменениям и нормализованной базе.

`prisma db push` и миграции не взаимозаменяемы без сверки провайдера и состояния схемы. Не применяйте `--accept-data-loss` вслепую. Откат приложения не отменяет изменение данных: восстановление БД планируется отдельно. Все варианты схем должны оставаться согласованными.

## Приёмка релиза

Зафиксируйте commit, успешные quality/integration/build/upload/verify, статус health и smoke-проход ключевого сценария. Для изменений Telegram отдельно проверьте тестовую доставку. Для схемы — резервную копию и сохранение идентификаторов/истории. В отчёте различайте «код в main», «сборка готова» и «релиз установлен».

## Дополнение 27 октября: обслуживание профилей

`profile-retention.yml` выполняет `scripts/profile-retention.mjs` через отдельный POST `/api/maintenance/profiles` с `X-30-0-Worker`. Используются уже настроенные `TELEGRAM_SERVERLESS_BRIDGE_SECRET` либо производный секрет из `TGCLOUD_TOKEN`; если они не заданы, workflow явно завершается ошибкой. Публичный health больше не запускает очистку. Поле `revision` health содержит git SHA, встроенный при CI build через `GITHUB_SHA`. При приёмке сверяйте его с коммитом релиза.

## SSH-сеть runner · 27 октября

Проверки и production build остаются на Ubuntu/Linux. Job передачи на Jino использует `macos-latest` как независимую сеть после повторных таймаутов Ubuntu runner. Он скачивает готовый Linux standalone artifact, упаковывает и передаёт его; нативные зависимости на macOS не пересобираются. Ключ, пользователь, SSH-порт, проверки и rollback Jino остаются прежними. Это изменение сети отправителя не гарантирует доступность хостинга; итог проверяется по upload и revision.
